# 发布更新器程序

更新器版本和 mod 内容版本独立。`publish-client` 仍只发布 mod；程序更新使用 `publish-updater`。

## 首次接入

将 2.2.0 或更新版本的 `更新mod.bat` / `更新mod.sh` 与 `_updater/mcmodsync.exe`、`_updater/mcmodsync.py` 一起发给玩家，覆盖同名文件。保留玩家原来的 `config.json`、`state.json`、`backup/`。旧更新器自身没有检查更新的逻辑，首次必须手动安装。

程序更新使用现有整合包源下的 `updater.json`，公钥沿用现有 `config.json`，不用另配下载地址。Windows 玩家需要含 Windows exe 的发布包；Linux 原生程序需要对应的 Linux 构建，Python 入口使用 Python 构建。

## 构建、预览、发布

在项目根目录运行（Windows 示例）：

```powershell
.\.venv\Scripts\python.exe tools/package_client.py --out dist/client-package-v2.2.0
.\.venv\Scripts\python.exe -m mcmodsync publish-updater --package dist/client-package-v2.2.0 --dry-run
.\.venv\Scripts\python.exe -m mcmodsync publish-updater --package dist/client-package-v2.2.0
```

后两条默认读取 `pack.local.json`，也可使用 `-c` 指定发布配置。`--dry-run` 读取线上发布信息并校验本地包，不上传。正式发布先上传程序，最后写入带 Ed25519 签名的 `updater.json`；发布失败不会提前切换指针。程序文件保存为独立的内容寻址对象，不受 mod blob 清理影响。

下一次修改更新器时，应同时提升 `mcmodsync/__init__.py`、`pyproject.toml` 和 `tools/make_release.py` 的程序版本（例如 2.2.1），重新构建、预览、发布。`build-info.json` 和实际程序的 `--version` 必须一致；同一版本禁止发布不同内容，防止部分玩家更新、部分玩家仍被判定为最新。

重新发布相同构建是幂等的。可以追加同一版本的另一平台构建，但已有平台的文件和 Python 入口内容必须保持一致。

## 玩家端流程

1. 双击入口，检查签名程序清单；没有发布程序更新或检查时网络暂不可用，则继续用当前程序检查 mod。
2. 发现更高版本时，仅从当前整合包源下载候选程序，核对 SHA-256 与大小；下载失败或签名错误时停止。
3. 旧程序以内部退出码 42 返回启动脚本，脚本等待旧进程退出，再调用已校验的新程序执行 `apply-update`。
4. 安装时再次验证签名、版本和文件哈希，备份并替换程序。失败时尝试恢复旧程序，保留配置、mod 状态和 mod 备份。
5. 脚本带着原来的参数启动新更新器，新程序确认版本后继续同步 mod。启动脚本最多允许两次程序切换，防止错误发布造成无限循环。

`verify`、`doctor` 和 `rollback` 不会触发程序升级。直接运行 exe / Python 的 `sync` 在发现新版时会返回 42；日常应通过新的双击入口运行，以完成安装与重启。

首次接入请在测试实例确认，特别核对窗口中的实际 mods 目录。自更新只替换固定的程序文件，不更新启动脚本或本地配置；以后若修改了启动脚本协议，需要另行发放兼容入口。
