# 故障排查与应急换钥

面向 OP。先按第 1 节定位问题，再按第 2 节处置凭证事件。**任何处置都以「玩家端不留在半更新状态」为前提**。

---

## 1. 通用排查顺序

1. **看退出码**（对照《玩家使用说明》表 / 下表），再决定是否动数据。
2. **看日志**
   - C 端：`<整合包>/_updater/logs/updater-<日期>.log`
   - B 端（服务端）：`<serverDir>/.mcmodsync/logs/`
   - A 端：终端输出 + `./.mcmodsync/logs/push-log.jsonl`
3. **只读优先**：先用 `verify`（C）、`push-server --dry-run`（A）、`doctor`（A）确认范围，再决定写操作。
4. **先保现场**：可疑时**不要**删 `_updater/backup/`、`history/`、`.mcmodsync-staging/`，这些是回滚依据。

---

## 2. 凭证泄露处置

> 总原则：**泄露即轮换**。删除文件无效——历史/备份里仍有；轮换后旧凭证立即失效。

### 2.1 Ed25519 签名私钥泄露（最严重）

影响：攻击者可伪造指针与版本清单，向所有玩家分发任意 jar。

```bash
# 1) 立即生成新密钥（不要覆盖旧文件，便于取证）
mcmodsync keygen --key-file ~/.mcmodsync/private.key.new
#    记下输出的公钥 B64

# 2) 更新 pack.local.json: signing.privateKeyFile -> 新私钥
#                         client.publicKey       -> 新公钥
# 3) 重新发布一次（让云端指针/清单用新私钥签名）
mcmodsync publish-client -c pack.local.json --version <比当前更高的 semver> --notes "换钥"
# 4) 重新打包玩家端（新公钥要写进 _updater/config.json）并分发
mcmodsync package-client -c pack.local.json
# 5) 通知玩家覆盖 _updater/ 后更新；未换钥的玩家会因验签失败（码 2）而无法更新 —— 这是预期
# 6) 确认无误后销毁旧私钥
```

**若私钥曾进入 git 历史**：`doctor` 会扫描并告警。仅删除文件不够，必须**重写历史或轮换密钥**
（推荐轮换，成本最低）。

### 2.2 对象存储 AK/SK 泄露

影响：攻击者可覆盖/删除 blob 与清单（清单签名仍能挡住篡改，但可造成不可用），并可能刷流量。

```bash
# 1) 控制台禁用旧子账号密钥，创建新子账号密钥（最小对象级权限）
# 2) 更新 pack.local.json: storage.accessKey / storage.secretKey
# 3) 自检并重发
mcmodsync doctor -c pack.local.json
mcmodsync publish-client -c pack.local.json --version <更高 semver> --notes "AK 轮换"
# 4) 核查桶内是否有异常对象（指纹不匹配的 blob 不影响一致性：内容寻址 + 签名）
```

### 2.3 CurseForge API key 泄露

```bash
# 1) console.curseforge.com 重新申请并撤销旧 key
# 2) 更新 pack.local.json: curseforge.apiKey
# 3) mcmodsync fetch-mods --dry-run 验证可用
```

注：`fetch-mods` 在 key 失效时会输出打码后的 key 与重新申请指引，并**跳过 CurseForge 源**、
其余 mod 继续，不会中断批次。

### 2.4 SSH 凭证泄露

轮换服务器账号/密钥 → 更新 `pack.local.json` 的 `server.keyFile`/`password` → `doctor` 复核。
SSH 凭证建议单独放 `ssh.json`（已被 `.gitignore` 覆盖）。

## 3. 桶被刷流量 / 被枚举

**现象**：CDN 或存储出流量异常增长；或有人能列出桶内对象。

**已知偏差（七彩云）**：T-00 实测发现该桶**匿名 `ListObjects` 返回 200**（可枚举顶层前缀与真实对象键），
违反「不可列举」硬约束。需求方已决策**接受偏差降级**，依据是：桶本身公开读（被列举内容本就可公开读取）、
Ed25519 签名是完整性/真实性主控、前缀随机化提高门槛。详见《七彩云配置》。

**加固手段（按代价从低到高）**
1. 确认 `prefix` 为高熵随机串（本项目为 `packs/<随机 16 位>/`），并**只**通过签名清单暴露路径
2. 主账号在控制台设置 **Bucket Policy**：显式拒绝匿名 `s3:ListBucket`（保留匿名 `GetObject`）
3. 轮换 `prefix`（等价于换目录），旧前缀对象清理
4. 启用 CDN 侧的访问控制/限额与流量告警
5. 若要求强保密：Bucket 改私有读，改用**签名 URL**（需改 A/B/C 三端与缓存策略，属方案变更）

**注意**：任何时候都不要把「保密性」寄托在桶不可列举上——签名的私钥才是信任根。

## 4. 服务端问题

| 码 | 含义 | 处置 |
|---|---|---|
| 4 | 磁盘空间不足 | `df -h`；调小 `historyKeep`；清理旧 history；再推 |
| 11 | staging 缺件或哈希不符 | A 端会自动重传 desired + 全部 blob 并重试一次；仍失败则看 B 日志的 staging 内容（是否有杀软/同步盘干扰） |
| 13 | 路径非法/穿越 | 检查清单里的路径（不得含 `..`、绝对路径、盘符） |
| 14 | 回滚目标不是最新 history 目录 | 列出 `history/<packId>/` 取最新；不要手工改名 |
| 15 | 目标 `changes.json` 已 rolled-back | 已回滚过，勿重复回滚；如需再回滚请指定更早版本 |
| 18 | staging 与 mods 不在同一分区 | 把 `.mcmodsync-staging` 放到与 `mods/` 同一分区（原子移入的前提） |
| 19 | 其他未分类错误 | 看 B 日志堆栈 |

**MC 服务器启动失败后如何止血**：
```bash
mcmodsync rollback-server -c pack.local.json   # 回滚到上一版本
# 手动重启确认 "Done ("；然后修正源目录 / mods.lock.json，再回到 push-server
```
期间**不要** `publish-client`——玩家端不受影响。

**服务器当前是否正常**：日志出现 `Done (` 即正常（每次重启后建议目检一次）。

## 5. 玩家端问题

| 现象/码 | 处置 |
|---|---|
| 3 游戏运行中 | 让玩家彻底退出游戏（含启动器后台） |
| 5 网络/重试耗尽 | 检查玩家网络与代理（支持 `HTTP_PROXY`/`HTTPS_PROXY`）；确认 CDN 可达 |
| 6 更新器过旧 | 重新 `package-client` 并分发 `_updater/`；玩家覆盖后重试 |
| 7 packId 不符 | 玩家拿了别服的分发包，重新发正确的 |
| 10 锁冲突 | 关掉重复的更新窗口 |
| 13 路径非法 | 清单异常，回滚发布并排查路径 |
| 验签失败（码 2） | 多为换钥后未分发新 `_updater/`；按 2.1 第 4 步处理 |
| 双击无反应/被杀软删除 | 用 `.py` 兜底：`python "_updater/mcmodsync.py" sync --target "<整合包根目录>"`；必要时按分支 B-02 采购代码签名 |

## 6. 换钥速查清单

- [ ] 新密钥/新凭证已在控制台生成，旧凭证已**撤销**
- [ ] `pack.local.json` 已更新（`client.publicKey` / `signing.privateKeyFile` / AK/SK / CF key）
- [ ] `mcmodsync doctor` 全绿（含「密钥对与公钥一致」「git 历史无凭证」）
- [ ] 已用**更高的 semver** 重新 `publish-client`
- [ ] 已重新 `package-client` 并分发 `_updater/`（含新的 `config.json`）
- [ ] 至少 1 名玩家试更成功并可进服
- [ ] 旧私钥/旧凭证已安全销毁，处置过程已记录（时间、原因、影响范围）
