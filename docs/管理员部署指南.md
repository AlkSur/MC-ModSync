# MC-ModSync 管理员部署指南

适用于 OP（服主/运维）。目标：让服务端 mods 与玩家客户端 mods 由**同一个版本清单**驱动，
增量同步、可回滚、全程签名校验。

---

## 1. 系统组成

| 端 | 角色 | 运行环境 | 主要文件 |
|---|---|---|---|
| **A** | OP 本机工具（CLI） | Python ≥ 3.10 + boto3/paramiko/cryptography | `mcmodsync/`（命令 `mcmodsync`） |
| **B** | 服务端执行器（非常驻） | 服务端 Python ≥ 3.8，**仅标准库** | 单文件 `<remoteBPath>`（由 `server/mcmodsync-b.py` 构建） |
| **C** | 玩家端更新器 | Windows 免安装（exe）；或系统 Python ≥ 3.10 跑 `.py` 兜底 | 分发目录 `_updater/` + `更新mod.bat`/`更新mod.sh` |

数据流：`mods/`（OP 源目录）→ A 上传工具（`fetch-mods` → `push-server` → `publish-client`）
→ 对象存储（指针 + 版本清单 + blob）→ 玩家端 C 拉取；服务端则经 SSH 由 A 直推。

---

## 2. 环境要求

**A 端（OP 本机）**
- Python ≥ 3.10（开发验证使用 3.13）
- `pip install -e ".[dev]"`（运行时依赖 boto3/paramiko/cryptography；dev 额外含 pytest/pyyaml/pyinstaller）
- 可 SSH 到 MC 服务器；可访问对象存储 endpoint 与 CDN

**服务端**
- Python ≥ 3.8（验证使用 3.11.2）；**无需任何第三方库**
- `<serverDir>` 与 `<historyDir>` 可写；建议低峰操作，推送期间 MC 可保持运行
- 单文件 B 由 A 端 `push-server` 自动引导（SHA-256 比对 → 上传 → `--protocol-version` 校验）

**玩家端**
- Windows：直接使用分发目录中的 `_updater\mcmodsync.exe`（免装 Python）
- Linux/macOS：`_updater/mcmodsync.py` + 系统 Python ≥ 3.10（或 `_updater/mcmodsync-linux`）

## 3. 首次部署（一次性）

### 3.1 生成签名密钥

```bash
mcmodsync keygen --key-file ~/.mcmodsync/private.key
```

- 私钥：`~/.mcmodsync/private.key`（POSIX 下权限 600），**永不外发、永不入库**
- 命中的公钥（Base64，32 字节原始 Ed25519）写入 `pack.local.json` 的 `client.publicKey`
- 密钥仅此一把；泄露处置见《故障排查与应急换钥》

### 3.2 配置 `pack.local.json`

以 `pack.example.json` 为模板，复制为 `pack.local.json`（已被 `.gitignore` 覆盖，**禁止入库**）。

| 字段 | 说明 |
|---|---|
| `packId` | 整合包唯一标识（如 `demo-pack`）。服务端、云端、客户端三处必须一致 |
| `packName` | 展示名 |
| `server.host/port/user` | SSH 连接信息 |
| `server.authMethod` | `key` 或 `password` |
| `server.keyFile` | 私钥路径（`authMethod=key` 时必填） |
| `server.password` | 密码（`authMethod=password` 时必填） |
| `server.knownHosts` | known_hosts 路径；未知主机默认**拒绝**，首次可用 `--accept-new-host` |
| `server.serverDir` | 服务端根目录（含 `mods/`），如 `/www/demo-pack1.1.12` |
| `server.modsDir` | 服务端 mods 子目录名，默认 `mods` |
| `server.sourceModsDir` | A 本机「服务端侧」源目录，默认 `./server-mods` |
| `server.remoteBPath` | 单文件 B 在服务端的落地路径，默认 `/www/mcmodsync-b.py` |
| `server.historyDir` | 服务端历史/备份根目录，默认 `/www/mcmodsync-history` |
| `server.historyKeep` | 服务端保留的版本目录数，默认 3 |
| `client.sourceModsDir` | A 本机「客户端侧」源目录，默认 `./client-mods` |
| `client.manifestUrl` | 云端**指针** URL，如 `https://<域名>/<前缀>/manifest.json` |
| `client.publicKey` | 签名公钥（Base64），写入玩家端 `config.json` |
| `client.clientStateFile` | A 本地发布状态文件，默认 `./client-publish-state.json` |
| `storage.endpointUrl` | 对象存储 S3 endpoint |
| `storage.region` | 区域（七彩云为 `us-west`） |
| `storage.pathStyle` | 是否 path-style 寻址（七彩云 path-style 与 virtual-host 均可用，实测选 `true`） |
| `storage.bucket` | 桶名 |
| `storage.prefix` | 关键前缀，如 `packs/<随机串>/`；随机前缀提高被枚举门槛 |
| `storage.accessKey/secretKey` | 子账号 AK/SK（**仅对象级权限**）。只写在本文件，禁止入库 |
| `storage.publicBaseUrl` | CDN 域名，如 `https://<bucket>.cdn.<provider>.com` |
| `curseforge.apiKey` | CurseForge API key（`source=curseforge` 时需要） |
| `signing.privateKeyFile` | 私钥路径（与 3.1 一致） |
| `concurrency.upload/download` | 并发数，默认 4 |

### 3.3 对象存储准备

1. 建桶（本项目生产环境为**公开读**桶，用于 CDN 回源）
2. 建子账号并授予对象级 `PutObject/GetObject/DeleteObject/ListBucket`
3. 规划关键前缀 `<prefix>`（建议随机串），结构：
   - `<prefix>/manifest.json`（指针，`Cache-Control: no-cache`）
   - `<prefix>/manifests/<version>.json`（版本清单，短缓存）
   - `<prefix>/blobs/<xx>/<yy>/<sha256>`（内容寻址 blob，`immutable`）
4. 记录 CDN 域名到 `storage.publicBaseUrl`

> 七彩云实测结论与偏差（匿名列举）见《七彩云配置》。当前已由需求方决策**接受偏差降级**：
> 认可「公开读 + 随机前缀 + 签名」模型。

### 3.4 服务器准备

```bash
# 服务端需 Python ≥ 3.8；目录可写即可（无需安装任何 Python 包）
python3 --version
```

`serverDir` / `historyDir` / `remoteBPath` 所在目录需可写。首次 `push-server` 会自动：
创建 `<serverDir>/.mcmodsync/`、`<serverDir>/.mcmodsync/logs/`、history 根目录，并上传单文件 B。

### 3.5 自检

```bash
python tools/check_config.py                 # pack.local.json 打码体检（逐字段核对是否已填/是否仍是占位符）
mcmodsync doctor -c pack.local.json          # 含 SSH+B 引导+协议版本+磁盘、对象存储往返+缓存头+CDN 匿名读
mcmodsync doctor -c pack.local.json --offline # 仅本地检查（配置/忽略规则/git 历史凭证扫描/密钥一致性）
```

`check_config.py` 只读且自动打码：SSH host/user/password、AK/SK、apiKey、publicKey 等敏感项只显示
「是否已填 + 字符数」，其余字段显示真值，并标出**必填但未填或仍为模板占位符**的项（退出码 1）。
首次配置、迁移机器或从模板复制配置后先跑它，可避免把 `YOUR_*` 占位符当成真配置使用。

`doctor` 会检查：配置完整性、`pack.local.json` 是否被 gitignore **且未被 git 追踪**、
git 历史是否曾提交过凭证、密钥对与公钥一致性、SSH/B/协议版本/磁盘、对象存储往返与缓存头、CDN 匿名读。

## 4. 首次发布流程

> **⚠️ 最重要的一条安全规则**：`push-server` 的语义是**让服务端 mods 与
> `server.sourceModsDir` 完全一致**——源目录里没有的 jar 会被**删除**（备份后可回滚，但会真实生效）。
> 因此**源目录必须先完整填充**，正式推送前**必须**先 `--dry-run` 逐条核对删除列表。
> 走查实测：源目录为空/不全时执行 dry-run，会列出服务端全部 176 个 jar 为「删除」项并给出
> 「服务端存在而客户端源目录缺少的 mod（176 个）」警告。首次接手已有服务器时，
> 请先把现有 mods 归入清单并拉齐源目录，再考虑推送。

```bash
# 1) 维护 mod 清单 mods.lock.json —— 字段与示例见《Mod获取策略》
#    最小条目（side: server|client|both；source: modrinth|curseforge|manual）：
#      { "name": "JEI", "side": "client", "source": "modrinth",
#        "projectSlug": "jei", "versionPin": "latest" }
mcmodsync fetch-mods -c pack.local.json                    # 拉取并按 side 落到 server-mods/ 与 client-mods/
mcmodsync fetch-mods -c pack.local.json --dry-run          # 只预览
mcmodsync fetch-mods -c pack.local.json --lock-manual      # 人工放置禁第三方下载的 mod 后锁定版本

# 2) 推送服务端（务必先 dry-run）
mcmodsync push-server -c pack.local.json --dry-run            # 零写，核对「新增/替换/删除」清单
mcmodsync push-server -c pack.local.json --check-server-client # 追加阻断：服务端有、客户端源目录缺 -> 码 1
mcmodsync push-server -c pack.local.json                      # 正式推送
#    然后手动重启 MC 服务器，日志出现 "Done (" 视为成功

# 3) 发布客户端清单与 blob（版本号自动递增，首次发布为 1.0.0）
mcmodsync publish-client -c pack.local.json --notes "首次发布"

# 4) 打包并分发玩家端（仅 C 程序更新时需要重新打包）
mcmodsync package-client -c pack.local.json
#    产物 dist/client-package/ 交给玩家覆盖到整合包根目录
```

> 版本号格式 A.B.C（A=大版本 1-9、B=版本类 0-9、C=小版本 0-6），缺省时自动在上一版
> 基础上 +1（C 满 6 进 B、B 满 9 进 A，如 1.1.6 -> 1.2.0）；也可用 `--version` 手动指定，
> 格式不符会报错。

**已被走查验证的命令行为**

| 命令 | 期望 |
|---|---|
| `fetch-mods --dry-run` | 输出三段式摘要（已更新/无需更新/需人工下载），零写 |
| `push-server --dry-run` | 打印变更预览与逐条清单，末尾明确 `[dry-run] 未执行任何写操作` |
| `publish-client --dry-run` | 打印本版变更与将上传的 blob/清单，零写；本地状态缺失时会尝试从云端恢复，404 视为首次发布 |
| `package-client` | 生成 6 个文件（含 SHA256SUMS.txt）并做 exe 产物核验，rc=0 |

## 5. 日常发布 SOP（原文 [13]）

1. 维护 `mods.lock.json`（字段表与示例见《Mod获取策略》），跑 `mcmodsync fetch-mods`；有 manual-needed 则按提示人工下载并 `fetch-mods --lock-manual`。
2. （可选）`mcmodsync doctor`。
3. （可选）`mcmodsync push-server --dry-run`。
4. `mcmodsync push-server`（推送期间 MC 服务器可保持运行，建议低峰）。
5. 手动重启 MC 服务器，观察日志：出现 `Done (` → 第 7 步；失败 → 第 6 步。
6. `mcmodsync rollback-server` → 手动重启确认恢复 → 修正源目录或 `mods.lock.json` → 回到第 4 步（期间**不发布客户端，玩家无感知**）。
7. `mcmodsync publish-client --notes "<说明>"`（版本号自动递增；大改版可 `--version` 手动指定）。
8. 仅 C 程序更新时重新 `package-client` 并分发 `_updater/`。
9. 通知玩家：双击「更新mod」，完成后手动打开启动器。
10. 找 1 名玩家试更并确认能进服。

## 6. 服务端目录结构（B 运行痕迹）

```
<serverDir>/mods/*.jar                 实际生效的 mod（平铺）
<serverDir>/.mcmodsync/state.json      B 的状态（已应用版本 + 文件清单）
<serverDir>/.mcmodsync/logs/           B 的运行日志（失败时先看这里）
<serverDir>/.mcmodsync-staging/        desired 与 blob 暂存（apply 成功后清空）
<serverDir>/.mcmodsync.lock            运行锁
<remoteBPath>                          单文件 B（升级时保留 .bak）
<historyDir>/<packId>/<版本>/          备份 + changes.json（回滚依据）
<historyDir>/<packId>/<版本>/rollback-drift/  回滚时发现的「手工漂移」文件
```

A 端推送日志：`./.mcmodsync/logs/push-log.jsonl`

## 7. 回滚

**服务端回滚**

```bash
mcmodsync rollback-server -c pack.local.json
# 之后手动重启 MC 服务器确认恢复
```

规则：目标必须是**最新且未回滚**的版本目录；三类反向操作（added→删除、replaced→还原、deleted→恢复）
带漂移保护——发现有人手工改过文件，会先移入 `rollback-drift/` 再处理，绝不静默丢弃。
成功后 `changes.json` 改名为 `changes.json.rolled-back`。

**玩家端回滚**（一般由 OP 指导操作）

```bash
# Windows
"%CD%\..\..\_updater\mcmodsync.exe" rollback --target "<整合包根目录>"
```

## 9. 凭证与安全

- `pack.local.json`、`ssh.json`、`~/.mcmodsync/private.key`、`client-publish-state.json` 一律**禁止入库**（`.gitignore` 已覆盖）。
- 泄露/轮换流程见《故障排查与应急换钥》。
- 对象存储建议最小权限子账号；桶为公开读时，保密性依赖**随机前缀 + 内容寻址 + Ed25519 签名**。
